# mcp-server: verification

Test cases for automation testers. Start each automated test's name with its `TC` ID.

## Test setup

- Test runner: Vitest, with unit tests colocated in `src/core`, and integration and e2e tests in `test/integration` and `test/e2e`.
- Each test uses a fresh temporary Git repository with one commit, a generated `.cclinic/sdd` with at least one spec, the cclinic skills installed, and a `tasks.db` saved through the task store.
- Integration tests talk to the server through the MCP SDK's in-memory client transport. E2e tests start `cclinic mcp` as a child process and talk to it over stdio with the SDK's client.
- A scripted test client declares elicitation support or not, records each question it's asked, and answers from a script (`approve`, `refine`, `review-doc`, `request changes`, `yes`, `no`, decline, cancel).
- No test calls real Claude. Auto-mode tests put the fake `claude` (`test/fixtures/fake-claude/claude`) on `PATH`, extended to tell the PM, QA and reviewer roles apart by prompt and return scripted verdicts, invalid JSON, costs, delays and exit codes, recording its arguments and working folder.
- Preview tests use an `.cclinic/environment/environment.json` whose `start` command is a small script that prints a URL, or exits 1.
- "A change at step X" means the workflow state was built through the tools, not written by hand, unless the test says otherwise.
