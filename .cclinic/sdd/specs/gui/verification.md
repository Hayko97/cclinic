# gui: verification

Test cases for automation testers. Start each automated test's name with its `TC` ID.

## Test setup

- Test runner: Vitest.
  - Unit tests are colocated in `src/core`.
  - Integration and e2e tests are in `test/integration` and `test/e2e`.
- Each test uses a fresh temporary project. Depending on the test, the project holds:
  - a Git repository with one commit
  - generated `.cclinic/sdd`
  - a `tasks.db` saved through the task store's plan save, with roadmap 1 holding two milestones and three tasks
  - fixture `.cclinic/auto/<run-id>/` and `.cclinic/workflow/<key>.json` files
- `HOME` is a sandboxed temporary folder.
  - Fixture transcripts go in `$HOME/.claude/projects/<dir>/<session-id>.jsonl`.
  - The fixtures include valid user, assistant, tool-use and tool-result lines, an invalid JSON line and an unknown-shape line.
  - One fixture contains a fake API key, to check redaction.
- No test calls real Claude. Tests use the fake `claude` on `PATH` (`test/fixtures/fake-claude/claude`), as automated-mode and roadmap-planning tests do. It records its arguments and can append lines to a transcript at the path its `--session-id` gives.
- Integration tests start the server with `--port 0 --no-open --json`, read the URL from stdout, and use `fetch` against `127.0.0.1`. Tests that need SSE read the event stream with a timeout.
- UI tests run the GUI's pages in a headless browser driven by the integration test, against a server on a temporary project. Pure UI logic (view models, follow/pause state, next step, status labels) is unit tested in core.
- Tests don't use real waits: refresh intervals come from constants that tests set low, or from an injected clock.
